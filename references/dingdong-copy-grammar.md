# 叮咚详情页文案语法与字数

只对叮咚好食光详情页使用本规范。先拆原文，再写候选；禁止先自由改写后反向补语法标签。

## 两阶段流程

### 快速审核

1. 递归列出产品目录文件名，一次性读取与文案事实有关的 Word、表格、PDF 和文本内容，并确认可用商品图片。
2. 只为读取正文或表格时直接提取文本，不渲染 Word，不创建提取脚本；仅在文本框、批注、嵌入对象或视觉排版会改变事实时渲染。
3. 查看能支撑本次卖点或食材描述的相关商品图片，记录图片可见事实；同类重复照片不逐张检查，不制作联系表或分析全部过程图。不要把图片无法证明的口感、香气或配料写成事实。
4. 写文案前必须上网查询相似产品的公开描述，记录可复核的来源和实际相似点。可原样采用短小、通用且符合当前商品事实的措辞；独特或较长的营销文字应重新写，不能把相似产品的配料、重量、功效或口感当成当前商品事实。来源和核对过程留在内部，不加到用户的两列初稿。
5. 读取一次已登记模板定义和索引，在内存中先核对本次任务范围、可改目标、受保护目标、固定文字和逐项目事实；根据目录文案、相关图片及相似产品的适用表达，在聊天中只生成 `板块｜新文` 两列初稿，只列本次可改板块。本次每个可改目标的“新文”必须有具体文字，供用户改写或要求重新生成；不能用空候选或提问代替初稿。用户确认当前两列表前不创建 `copy.json`、审核文件、任务文件或 PSD 工作副本。
6. 在写完整候选前扫描正式品名、逐字步骤和普通适配文案中的冲突术语；内部记下冲突并尽量完成不受影响的文案。只有冲突直接妨碍用户审核或正式制作时才集中询问，不得先构建完整生产 JSON。

### 正式生成

1. 仅在用户解决冲突并确认初稿方向后创建一次 `copy.json`。
2. 使用标准脚本一次完成合规校验和正式九列审核；失败时修改具体失败项，不得把 `structure-adapted` 改成 `verbatim` 绕过语法、分句或换行校验。
3. 用户说“确认文案”“文案确认”“按这个套版”时，确认对象是当前已展示的两列表。把正式九列审核稿中本次可改板块的新文与该表逐项比较，并在内部校验模式、语法、字数与保护范围；文字一致且校验通过后，直接使用脚本生成的 SHA-256 创建详情页任务并套版，不再请求用户确认哈希、任务或 PSD 写入。正式九列审核稿只供内部核对，用户未要求时不展示。
4. SHA-256 只证明确认后的文件未变化。若正式审核稿与已确认表不一致或校验失败，展示差异并停止；不得自行改文案后继续。
5. 详情页任务只复验该文件、哈希和目标绑定；不要重新读取资料、图片或模板索引。
6. 主图只复用已验证详情页和固定 mapping；不要重新做产品事实或文案分析。

### 确认阶段修改与重新生成

1. 用户对两列候选提出修改、重写、换一种说法或重新生成时，把需要生成的行恢复为未确认状态。确认阶段的重新生成不是自由润色；必须先回到模板原文和当前产品事实，再完整执行初稿的资料门槛、审核顺序、语法、分句、字数、事实依据、逐字来源、术语决策、版块专属规则、固定文字与受保护范围。已经检索并核对过的相似产品来源在同一任务中复用，不重复搜索；只有用户改变产品定位或要求新的参考方向时再搜索。
2. 只重新生成用户明确点名的行及确有事实、术语或跨行唯一性依赖的联动行，未点名行逐字符不变。不得沿用旧候选的句式后反向补标签，不得把 `structure-adapted` 改成 `verbatim`，也不得因用户在确认阶段催改而放宽任何初始规则。
3. 用户亲自给出本次可改目标的完整文字，或针对当前两列表指定“把 A 改为 B”“就按这个字样”等精确替换时，按用户字样逐字符保留；只要不触碰永久只读或固定文字，就把合并后的目标全文登记为 `verbatim`，令 `sourceText` 与最终文字逐字符一致，并记录用户原话 `userInstruction`。代理自行重写的部分仍须按 `structure-adapted` 校验，不得借用户只指定一个短语而把其他自拟文字伪装成逐字来源。校验失败时在内部记录具体原因，不得静默修正后宣称已按用户原文处理。
4. 每轮修改后在内部重新计算新文语法和字数，并重新展示每个可改目标都有具体新文的完整两列表；资料或硬性规则仍有缺口时内部记录具体问题，必要时集中询问，但不以空候选代替文案。若用户已经确认过上一版，任何后续修改都使上一版两列表、正式审核稿、`copy.json`、SHA-256、任务及套版授权失效；必须等待用户确认新两列表后，才可为新版本生成正式文件和写入 PSD。

## 资料发现门槛

1. 用户给出目录时先递归列出文件，识别 Word、表格、PDF、文本、图片和 PSD；一次性读取与产品文案有关的全部文档内容。
2. 同时读取已登记详情页模板的定义和当前索引，取得真实原文、目标 ID、完整路径、行数和换行。
3. 事实优先级为：用户指定逐字文本、当前产品资料原文、当前产品图片可见事实、明确标注的推断。相似产品网页只提供措辞参考，不是当前商品事实；未经用户批准的推断不能写入候选。
4. 完成目录与模板盘点前，不得根据目录名判断正式品名，也不得宣称“只有目录名／一句说明”或“资料不足”。
5. 先从目录文字、相关商品图片和已核对的相似产品表达中，为本次每个可改目标写出有内容的审稿文案；不得以“无候选”“无合规候选”“待补充”、空白或提问代替新文。现有材料不足以满足某项模板硬性规则时，可用已知事实提出克制的文字方向，在内部准确记录未通过的规则和需要补充的事实；该行只能供用户修改，不得假称合规或进入正式生成。需要额外事实时集中问一次，不编造商品事实或降低正式校验标准；若用户确认该事实不存在，保留审稿文案并停止该目标的正式生成，不提出即使获准也无法解除限制的授权请求。

## 审核顺序

1. 从当前模板索引读取准确 `id`、`path` 和 `oldText`。
2. 把逐字来源写成 `verbatim`；`text` 必须逐字符等于 `sourceText`。
3. 把普通改写写成 `structure-adapted`，逐行填写原文和新文的分词。
4. 每个词组填写 `pos`：`noun`、`verb`、`adjective`、`adverb`、`number`、`unit` 或 `fixed`。
5. 每个词组填写具体 `role`，例如 `aroma`、`degree`、`ingredient`、`texture`、`method`、`action`、`scene`。
6. 保持对应词组的 `pos`、`role` 和 `separatorAfter` 完全一致。每个对应词组及由空格或标点分隔的分句都只允许相差 1 个可见字符。
7. 为每条替换填写 `evidenceIds`，只引用当前产品 `facts`。旧品词命中当前事实时才允许保留。
8. 先在聊天中只展示 `板块｜新文` 两列初稿；原文、语法、字数、事实依据、相似产品来源和保护范围留在内部核对。用户确认当前文案后再生成一次正式九列审核稿；其中本次可改目标的新文与已确认两列表逐字符一致且内部校验通过，即可直接生成详情页任务，不再要求用户确认 SHA-256。

## 板块合并展示与信息去重

1. 聊天待改文案只显示 `板块｜新文` 两列，每个本次可改板块一行，不列受保护文字、原文、语法、字数、依据、状态或相似产品来源。`new-dingdong-copy-review.ps1` 的正式九列审核稿仅供内部验证；同一板块内多个 Photoshop 文字目标仍分别保留在 `copy.json`。
2. 禁止把标题单独展示。版4的主料标题与口感说明合并为“版4”，版6的主标题与两条说明合并为“版6”；头版、步骤版及其他含多个可改文字目标的板块同样合并。新文单元格按 PSD 阅读顺序使用 `<br>` 保留内部换行和先后关系。
3. 拟写前先为同板块各文字目标分配不同的信息焦点，例如标题写核心食材或搭配，说明写口感、风味、色泽、场景或利益点。标题与下方说明不得使用同词或近义词重复描述同一外观、口感、风味或卖点；“完整/颗颗成形”与“圆润/饱满”等指向同一外观焦点时也视为重复。
4. 发现上下描述重复时，内部记录 `duplicate-board-copy-focus`，只重写发生重复的目标，不改动同板块已合规文字或其他板块；展示两列表前完成语义去重，不能依赖字面查重，也不能等正式脚本通过后忽略。
5. 所有两段式标题及标题与下方说明组成的两段文案，上下段的开头词语或句式片段必须不同。按实际阅读顺序比较首个有意义的词语及开头短语，忽略段首空格、编号和装饰标点；不得用添加空格、标点或拆分词组来掩盖重复。不论两段在同一文字层还是不同文字层，都在初稿、每轮修改和套版前检查；不得仅因共享一个汉字就误判为开头词语相同。命中时在内部记录“上下段开头重复”，按模板语法、字数、事实和信息去重规则修改发生重复的候选，未受影响的文案保持逐字符不变。

普通改写 `structure-adapted` 严格禁用完整二字“入+名词”词组。检测以 `proposedSegments` 的词组边界为准：某一词组的 `text` 恰好为“入”加一个中文字符时，`入味`、`入锅`、`入口` 等返回 `forbidden-ru-noun-pattern`。不要把应当独立成词的二字结构合并进更长词组来绕过。`加入香菜`、`放入蔬菜` 和被空格拆开的 `入 味` 不命中。用户指定的逐字来源 `verbatim` 必须原样保留，因此不应用此禁写规则。用户对当前审核稿明确指定完整短语或“A 改为 B”也属于逐字来源；合并后的目标全文以 `verbatim` 登记后，可包含“入味”等指定字样。该例外只覆盖用户实际指定的最终文字，不得用于代理自行生成或扩大改写。

版4的 `structure-adapted` 文案永久禁止描述预制处理、切配完成或包装分份状态。出现 `分装`、`装好`、`切好`、`整包`、`配好`、`备好`、`预切`、`切配`、`预处理`、`预制`、`预装`、`按包`、`单包`、`包装`、`袋装`、`盒装` 等同类词时返回 `forbidden-block4-prep-packaging-copy`。版4也永久禁止复述使用步骤、火候、时长或烹饪动作；出现 `步骤`、`锅中`、`另起锅`、`热锅`、`冷油`、`大火`、`中火`、`小火`、`下锅`、`下入`、`放入`、`加入`、`倒入`、`倒出`、`备用`、`翻炒`、`炒制`、`煸炒`、`炒香`、`煮制`、`蒸制`、`焯水`、`断生`、`变色`、`上色`、`分钟`、`秒钟` 时返回 `forbidden-block4-instruction-copy`。两类检测都作用于版4完整新文并在正式审核、任务生成和准备工作副本前三次复验；不得拆分词组绕过。未命中关键词但语义仍在复述步骤时，展示两列初稿前也必须在内部阻断并重写。版4只写食材特征、口感、风味或成品表现。逐字步骤和其他版块不应用此规则。

版6两个说明目标永久各自描写一种不同配菜。为每种配菜事实填写 `category: "side-dish"` 和非空 `terms`；每个说明的 `evidenceIds` 必须引用且正文必须命中恰好一种配菜事实的词，两个说明不得绑定同一配菜。缺少配菜事实返回 `missing-board6-side-dish-evidence`，正文未命中配菜词返回 `board6-side-dish-term-missing`，单项混写多种配菜返回 `ambiguous-board6-side-dish-copy`，两个说明重复同一配菜返回 `duplicate-board6-side-dish-copy`。不得把酱汁、主料或步骤说明写入这两个目标。

版6主标题的正文前两个字符永久固定为“特调”。模板定义通过 `requiredPrefix: "特调"` 登记该要求；正式文案校验和 Photoshop 前置校验都会以 `required-copy-prefix` 拒绝“秘制”“双料”等其他开头。此规则只固定开头两字，其余版6标题仍须按原语法、分句、字数及当前产品事实适配。

版8场景文案永久逐字符固定为两行“下班回家轻松煮”“煮好后热乎上桌”。模板定义通过 `requiredText` 登记 Photoshop CR 形式的完整正文（含末尾 CR）；正式文案校验和 Photoshop 前置校验都会以 `required-exact-copy` 拒绝“5分钟热乎上桌”等其他文字、行末空格或不同换行形式。此目标不再按产品事实改写。

给用户展示待改详情页文案时，只使用 `板块｜新文` 两列并只列本次可改板块；不附其他列、保护文字或内部审核说明。每个本次可改目标的新文都要有具体文字。正式九列审核稿及来源、事实、语法、字数、保护和阻断核对只在内部使用；不得用空候选占位或营销推断填补。

逐字步骤不受普通文案的字数对齐规则约束。只读文案审核不能断言它在 PSD 中溢出；必须在保持原字号写入工作副本并查看实际预览后判断。步骤遮挡只记为警告，不阻断提交，也不得触发缩字、改写或请求用户提供短版。按确认稿直接完成 PSD；最终逐个步骤报告“全部可见”，或写明实际可见终点并逐字符引用被遮挡的完整原文。不得只按字数估算遮挡范围，边界字符显示不完整时计入被遮挡部分。

多行文案的 `lines` 数量必须与原文和新文的非尾随空行数量一致。标点、空格放入前一词组的 `separatorAfter`；对应分隔符必须完全相同。PSD 文字末尾自带的连续换行由脚本单独计数，原文和新文必须一致，不要为尾随空行伪造词组，也不要改成 `verbatim` 绕过。

模板通过 `protectedTextTargets` 或 `protectedPathPrefixes` 声明的全部文字永久只读，版2只是其中一部分。不得询问用户是否解锁；即使用户明确授权，也禁止修改，禁止填写非空 `protectedOverrides`，禁止用通配符、路径前缀或手写任务绕过。唯一例外是已在主图定义中注册 `allowStepCountSync` 的画板3步骤数量标题：实际步骤经验证为唯一且从 1 连续编号时，只可将模板标题中唯一的 `N步` 数字同步为已登记的 1、2、3 或 4，其他字符、字号、版式不变；数字已经一致时保持原文，未登记数量或扩大改写返回 `invalid-step-count-sync`。其余受保护位置检测到与模板原文不同就立即报错，并由用户自行在 Photoshop 中修改。

当资料同时出现“肉末／肉沫”等冲突术语时，快速审核阶段先阻断并询问。用户确认后填写 `terminologyDecisions`：普通改写在 `allowedByMode` 中指定允许形式；若不同逐字来源必须分别保留不同写法，在 `allowedByReplacement` 中为每个目标填写准确 `id`、完整 `path`、`allowedTerm`、`evidenceIds` 和用户原话 `userInstruction`。不得全局自动纠错。
